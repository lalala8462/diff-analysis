# 分析管线 v4.1：关系图、证据供给与评审反馈

> 更新日期：2026-10-23。基于现有初版增量完善，采用“先补齐首期评审流程”的方向。本文是待实施设计，不表示下述修复和新能力已经完成。保留 Python 主流程、Java 分析器、SQLite 和本地命令行。

## 1. 范围、依据与现状差距

产品边界以 [功能规格](../specs/001-change-impact-review/spec.md) 为依据：各项目两个指定版本的最终净差异是唯一变化底账；比较范围内的提交只解释来源和可能需求；代码依赖来自指定版本；人工与 AI 结论分别保存。

首期不分析更早历史的共同修改和历史依赖演进，不构造预计合并树，不执行待分析项目的构建、业务或脚本，不默认引入 Web 或发布门禁。用户提供的 SHA 集合是评审组合；部署组合未知时保持未知。

当前实现见 [review.py](../diff_analysis/review.py)、[release_analysis.py](../diff_analysis/release_analysis.py)、[release_report.py](../diff_analysis/release_report.py)、[cli.py](../diff_analysis/cli.py) 和 [wizard.py](../diff_analysis/wizard.py)。以下为静态核对及用户反馈形成的差距清单，本轮未执行缺陷复现或效果测试。

| 缺口 | 当前情况 | 本设计的补齐方向 |
| --- | --- | --- |
| G1 / P1 关系路径漏项 | 多源遍历每节点仅保留一条路径，组间检查依赖摘要，可能漏掉同时变化的 A 调用 B | 两侧分别持久化节点和边；图查询计算影响，路径仅用于展示 |
| G2 / P1 模型证据不足 | 变化附近代码及关联名称不足以核对消费者；部分列表限制为 30 项而未计入截断标记 | 相关完整方法、契约及两端代码按需取证；整个输入预算及逐类缺口 |
| G3 / P1 消费者输入不统一 | 向导拒绝同 SHA；旧版未解析调用只保留数量；跨项目名称／参数匹配较弱 | 项目角色、两侧固定版本和关系判定契约统一 |
| G4 / P1 底账失败隔离不足 | 主入口先扫描再产出新底账，JDK／扫描器整体失败可能阻断报告 | 先保存 Git 底账，再独立增强；按项目和阶段保留部分结果 |
| G5 / P2 评审闭环不完整 | 未接入独立预期目标；运行索引不足以保存对象级判断和修订 | 目标、对象、人工／AI 判断与适用范围独立版本化 |
| G6 / P2 分组碎片与调整不足 | 唯一任务号候选合组，否则逐差异保留；未完成人工拆合流程 | 归组建议、细分评审单元、人工修订及受影响结果重算 |
| G7 / P2 效果评估不足 | 登记与降级案例多，分组、影响、噪声和规模评测不足 | 预先标注样例、对照审核、明确规模和预算配置 |

## 2. 总体流程与失败隔离（G4）

~~~mermaid
graph TD
    A["创建批次并固定项目角色、两侧 SHA"] --> B["先保存 Git 文件事件与最终差异"]
    B --> C["保存两侧代码证据及阶段清单"]
    C --> D["独立增强：AST 与两侧关系边"]
    C --> E["独立增强：范围内提交及候选来源"]
    D --> F["候选需求组和图上的交叉检查"]
    E --> F
    F --> G["按需取关联方法、契约和消费者代码"]
    G --> H["准备有完整预算记录的证据包"]
    H --> I["可选 AI 分析"]
    H --> J["人工报告"]
    I --> J
    K["用户输入或确认的预期目标"] --> L["独立确认与符合性复核"]
    J --> L
    L --> M["记录修订、分歧及需重新核对的结论"]
    D -.-> N["失败时保留底账、阶段缺口和部分报告"]
    E -.-> N
    I -.-> N
~~~

执行顺序必须落实到入口，而不只在报告中承诺：

1. 建立运行目录、批次清单和项目状态；逐项目解析 Git SHA，明确失败项目。
2. 先枚举并落盘 Git 最终文件事件及 Hunk，再提取可读取的两侧代码。底账无需 JDK。
3. 每个文件保存提取结果；二进制、Gitlink、纯重命名、解析不支持、超限和读取失败都留下事件或缺口。
4. AST、提交来源、关系、分组、取证、模型等阶段分别执行和保存。单项目／单阶段错误不能抹去已完成结果，其他可独立项目继续。
5. 报告可由持久化证据重建；JDK 不可用时仍能生成仅含 Git 事实及缺口的报告。旧格式报告失败也不能阻断已落盘的新底账。

每阶段保存 status、输入指纹、输出引用、起止时间、错误和 omissions。状态为 `NOT_STARTED`、RUNNING、COMPLETE、PARTIAL、FAILED、SKIPPED；仅在产物成功保存后标 COMPLETE。模型未启用属于预期 SKIPPED，不因此把已完成静态阶段改成失败。

批次区分 COMPLETE、PARTIAL、FAILED、RUNNING。Git 不可访问或 SHA 不能解析时，不伪造空底账：该项目明确失败，批次可保留其他项目的部分结果；所有项目均无有效底账时为 FAILED。报告生成状态独立于分析状态，存在 Markdown 不等于分析完整，分析成功而渲染失败时允许只重做渲染。

## 3. 统一输入与两侧版本（G3）

所有入口最终使用同一批次模型，而不是分别维护向导和非交互语义。

| 字段 | 约定 |
| --- | --- |
| project_id / repository | 稳定项目身份及可访问仓库 |
| role | CHANGE：待审核变化项目；EVIDENCE：为关联检查提供代码证据的项目 |
| base_sha / head_sha | 每侧完整固定 SHA；EVIDENCE 允许两侧相同，不再被“无变化”规则拒绝 |
| comparison_policy | FINAL_NET_DIFF；方向显式保存，不因分叉静默替换为其他差异语义 |
| scope / deployment_binding | 本次用途、纳入范围及部署对应关系的证据或 UNKNOWN |
| target_refs | 关联的预期目标及其修订；没有目标时为空，不能从提交说明自动填成权威需求 |

CHANGE 的净差异也可能为空，不凭提交说明生成需求。EVIDENCE 两侧若不同，净变化仍要登记，明确是否属于本次待审核变化；范围未确认时标 `SCOPE_NEEDS_CONFIRMATION`，不静默丢弃或自动当成待上线需求。相同 SHA 可以复用一次扫描，但仍分别保留 BASE／HEAD 的侧别引用。

用户纳入但没有变化的项目，不要求先产生需求组才能参与影响分析。未纳入、版本未知或读取失败的消费者分别登记覆盖缺口，不默认取主分支、最新版本或生产版本。

现有 `--catalog` 是单 SHA 消费者的兼容入口。迁移时将它转换为 EVIDENCE 项目并在两侧引用该 SHA；向导和后续批次输入均需支持相同角色语义。接口和参数的最终名称在实施任务中确定，本文不宣称已有新参数。

## 4. 从关系边计算影响（G1、G3）

### 4.1 数据契约

每侧保存独立的节点、调用点、关系边和未解析调用；旧版未解析调用必须保存具体记录，不能只保留数量。

- 节点：project_id、snapshot_sha、element_id、kind、symbol、代码证据引用。
- 边：edge_id、调用方与被调用方、两端项目／SHA、side、kind、调用点证据、解析方式及限制。
- 跨项目关系还保存依赖包／接口／实现或服务绑定证据；不能绑定时明确缺少哪一段。
- 图版本记录扫描器、解析配置、覆盖及构建状态。BASE 与 HEAD 的关系不拼接为一条版本内真实路径。

关系类型区分 `RESOLVED_CODE_RELATION`（支持范围内有充分绑定证据的代码关系）、`STATIC_CANDIDATE`（名称／参数数量等弱线索）、`BINDING_UNCONFIRMED`（接口已知但实现、包或服务绑定未确认）。类型和证据级别分别保存，名称匹配不能自动升级。当前扫描器的简单类型名与参数数量匹配也不能统一标为完整 Java 类型解析。

首期最低支持：保存当前可识别的 Java 调用点和候选边，逐步补范围明确的类／方法绑定；继承、重载、注入、代理及跨服务不能解析的部分持续显式降级。SQL、MQ、Redis 等文件变化先入账，资源同名不作为已解析依赖。

### 4.2 查询与展示

边方向固定为“调用方 → 被调用方”，影响从变化对象向上游消费者传播。组归属标记在节点／评审单元上，独立于路径展示。

1. 直接检查边的两端，若属于不同变化组，生成交叉候选。A 调用 B 且两者都变更时必须保留 A → B，不能因二者同时是遍历起点而跳过。
2. 传递影响按来源组传播标记。visited 至少区分节点与来源组，或使用等价的来源集合传播；环路可用强连通分量处理，不需要枚举全部路径。
3. 对同一消费者保存多个变化来源。共同调用方、菱形路径和多源交汇不能因先到达者而丢失其他来源。
4. 先发现关联节点、边和来源，再选择有限代表路径用于报告。展示路径数量不决定影响识别范围。
5. 在 BASE、HEAD 分别查询未变更消费者和组间关系。旧版有而新版消失的关系仍要检查；跨版本无法确认元素映射时保留两侧候选，不以同名强制认定同一对象。
6. 图构建、节点展开、来源传播、候选匹配及展示各自有预算和缺口记录。已知直接边不能因路径摘要截断而消失；发现阶段触顶时不得显示“没有影响”。

交叉项包含变化源、关联对象、所属版本、边／路径证据、缺失绑定和核实问题。它表示需要联合检查，不自动认定缺陷，也不自动合并需求。首期“跨提交线路”仅辅助解释已提交代码中的交叉，不开展预计合并或重建冲突解决过程。

## 5. 按需取证与整个模型输入的预算（G2）

### 5.1 阅读窗口与分析证据

前后各 30 行是快速阅读窗口，不是业务上下文的固定边界。根据待判断问题逐步获取：

| 证据类别 | 取证内容 |
| --- | --- |
| DIFF | 原始净差异、两侧位置及快速阅读窗口 |
| METHOD | 变化所在完整相关方法、必要调用方／被调用方法及关键分支 |
| CONTRACT | 相关类型、枚举、DTO、接口签名、字段语义及已提供的契约 |
| CONSUMER | 未变更消费者的真实代码、判断条件和取证版本 |
| RELATION | 调用点、交叉两端代码与绑定依据；只有名称时保留缺口 |
| HISTORY / TARGET | 范围内的提交说明、候选来源、预期目标与约束 |

所有代码证据包含 `evidence_id`、project_id、固定 SHA、侧别、路径、范围、内容摘要／哈希、提取状态和截断范围。上下文扩展不改变原始 `diff_id`。同一代码块可复用证据引用，原始版本内容不得被模型摘要替代。

例如 A 改返回状态而 B 未修改，分析“B 是否仍按旧状态处理”至少需要 A 的状态变化、相关类型／契约和 B 的处理代码。只有 B 的方法名时只能产生待补证据问题。需要更深调用或外部绑定时继续按需取证；无法取得就停止相应判断，不假装已覆盖整条业务链。

首期可用有界图扩展和完整方法提取；模型后续可请求已授权范围内的证据 ID／对象，统一由只读取证器处理并记录请求。无需让模型任意执行工具或读取未纳入版本。

### 5.2 输入与缺口清单

预算覆盖最终实际发送的全部内容：任务提示、目标、变化、方法、类型、关系、消费者、提交说明、元数据和引用清单。还要计调用次数、补证轮次并为输出预留空间。

优先使用模型对应的 tokenizer；没有可靠计数器时可以使用明确标注为字符数的保守预算，不把字符数伪称 token 数。打包后重新检查序列化请求；关键双端证据不能通过静默裁切变为单端事实。过大的方法可提供明确分段，标 PARTIAL，记录剩余范围。

每类保存 `total_known`、`provided_ids`、`partial_ids`、`omitted_ids`、原因和预算占用。清单过大时完整记录到证据目录，输入中保留数量、清单引用及自身截断状态；上游发现不完整时另记 `discovery_incomplete`，不虚构未知对象总数。

任何类别被省略、部分提供或上游未完全发现时，总体 `truncated`／`coverage_incomplete` 必须反映。31 个关联项与 31 个消费者只提供各 30 个时，必须分别登记两个缺失对象；提交说明、类型、单行长度、关系两端、组数上限和补证失败均适用，不能只统计 dropped `diff_id`。

模型结果需引用输入中实际提供的 `evidence_id`，同时关联 `diff_id`／评审单元。结构校验仅证明引用存在及适用版本；能否支持论断还需检查双端证据、必要契约、分析范围及人工／独立复核。判断涉及的必要证据不足时为 `INSUFFICIENT_EVIDENCE`，不能输出确定缺陷或无影响。

模型默认不启用；未运行、调用失败、预算未分析和部分分析分别记录。现有输入的约 24,000 字符及部分列表限制仅是当前实现，尚不满足上述全量预算设计。具体供应商兼容性仍需独立验证。

## 6. 需求目标、独立评审与重审（G5）

### 6.1 两类目标与符合性

CandidateGoal 是从代码和提交归纳的候选目标；ExpectedGoal 是用户提供或人工明确确认的预期目标与约束。两者分别版本化，保留来源、文本／附件哈希、作者和时间。

首期延续 CLI／文件输入：允许导入文本或结构化目标，明确输入输出、允许变化、必须保留的行为和不变量；再绑定到组或影响对象。人工修订和确认目标时保留旧版本及理由，不覆盖历史。

~~~mermaid
graph TD
    A["固定代码证据"] --> B["归纳候选目标"]
    B --> C["人工核对并修订需求理解"]
    D["用户输入的预期目标与约束"] --> E["保存预期目标修订及确认来源"]
    C --> E
    A --> F["行为和潜在影响检查"]
    E --> G["针对该目标开展符合性复核"]
    F --> G
    G --> H["分别保存人工与 AI 判断和分歧"]
    E -.-> I["目标修订后，原符合性结论需重审"]
~~~

AI 对自身推测的认可不证明符合真实需求。没有 ExpectedGoal 时仍可讨论代码行为和潜在影响，但是否超出需求为 `UNDETERMINED`。预期目标修订后，针对新约束开展新的符合性复核，不把代码观察倒推为已授权需求，也不回溯修改旧批准记录。

### 6.2 分对象、分维度记录判断

| 评审维度 | 确认内容 |
| --- | --- |
| GROUPING | 单元归属、拆分／合并是否合理 |
| REQUIREMENT | 需求理解及预期目标是否准确 |
| IMPACT | 某条关联或影响判断是否被证据支持 |
| CONFORMANCE | 当前变化是否满足指定预期目标与约束 |

每条 ReviewDecision 绑定 object_type／object_id／object_revision、dimension、actor_kind（HUMAN／AI）、判断、理由、引用证据、目标修订、操作者或模型身份、时间和适用范围指纹。未完成、证据不足、认可、否定等分别表达；存在分歧时保留双方记录，不汇总成一致通过。一个维度通过不能代表其他维度完成，AI 完成不能替代人工确认。

决定以追加记录保存；修订通过 `supersedes` 指向旧记录。AI 需求生成结果和 AI 复核记录也要区分用途，不把生成文本等同复核通过。

适用范围指纹由结论实际依赖的项目版本、单元、组、图／证据、ExpectedGoal、模型输入和分析规则修订构成。任何依赖修订后，旧结论仍可查看，但当前适用性标 NEEDS_REVIEW。SHA 未变而分组、需求解释、模型输入或证据改变，也要按依赖重新判定。

原始事实没变时不必重采集全部源码；可以重用事实证据，但重建受影响的组、交叉项、输入与结论，不能靠运行目录或 SHA 相同直接沿用旧批准。

## 7. 可解释分组与细分评审单元（G6）

保留现有保守分组作为底线，增加可接受／拒绝／修订的 GroupSuggestion。每条建议包含相关单元、建议动作、正反依据、证据引用和限制。任务号、语义对象、调用上下文、测试／契约和提交说明可提供建议；时间接近、同文件或存在调用边不能单独决定合组。

优先在局部候选中生成建议，避免通用工具方法把所有变化连成大组。没有任务号时仍应尝试有依据的局部归组，无法判断才独立保留；按组大小或数量压缩不等于分组正确。

RawHunk 是不可改写的原始底账。ReviewUnit 是可细分的评审对象：

- 一个 RawHunk 可映射多个 ReviewUnit，每个单元保留父 Hunk、两侧子范围及修订。
- 一个单元有一个主要展示组；共享影响通过关联引用，底账数量不因多组展示重复计算。
- 拆分时校验原始变化范围的覆盖，未能分配的部分显式保留待审单元。重叠证据可以复用，重叠变化归属需说明共享原因。
- 行级无法独立切开的逻辑可保留同一父 Hunk 并附多条需求引用，不伪造可独立应用的 Git 补丁。

首期提供本地命令或可编辑的结构化修订文件，支持拆单元、拆组、合组和调整归属；具体命令在实施时确定，不以 Web 为前提。保存操作者、理由、原／新归属及影响对象，重建相关模型输入和评审适用性。用户修订不反向改写待分析仓库。

## 8. 持久化、报告与阶段契约

### 8.1 逻辑实体与存储边界

以下为拟议实体，不是已存在的数据库表声明；实际迁移按阶段增加，保留已有基线和运行索引数据。

| 实体 | 主要内容 |
| --- | --- |
| ReviewBatch / ProjectVersionPair / StageResult | 项目角色、范围、两侧 SHA、配置、阶段状态和缺口 |
| RawChange / ReviewUnit | 原始 Hunk／文件事件、细分范围及父子追溯 |
| RelationGraph / RelationEdge / UnresolvedCall | 两侧图、绑定依据、覆盖和查询缺口 |
| Evidence / EvidenceManifest | 固定版本代码、契约、取证状态、已提供与未提供清单 |
| RequirementGroup / GroupSuggestion / GroupRevision | 候选归属、建议、人工调整及审计 |
| CandidateGoal / ExpectedGoal / ImpactFinding | 候选意图、权威目标修订、影响及证据 |
| ModelRun / ReviewDecision | 输入输出、模型状态、独立判断、理由和适用性 |

SQLite 存批次、修订和评审记录；大块原始代码及模型输入输出作为运行目录中的不可变证据文件，用哈希引用。已有 `baseline_snapshot` 只表达版本扫描／基线事实，`analysis_run` 目前只存目录和摘要，二者不能代替上述评审表。持久化需要显式 schema 迁移，不能因模型结论把基线改为已批准。

每阶段写入完成清单后再提交完成状态。文件和数据库无法同时提交时通过产物哈希与阶段清单恢复，不将半写入文件当成功。规则／扫描器变更使相应派生产物失效；按固定 SHA／blob、工具版本、配置和输入指纹复用缓存。

### 8.2 输出与阅读顺序

每次分析创建 `.diff-analysis/runs/<UTC日期时间>-<随机标识>/`，报告标注时区；例如 `20261023T030000Z` 对应北京时间 2026-10-23 11:00。运行目录不可因重跑覆盖，原 `--output`／`--json-output` 继续作为旧格式兼容输出。

当前已生成 `report.md`、`analysis.json`、`evidence/D-*.md` 和 `model_inputs/G-*`。拟增加阶段清单、关系和证据清单、目标及评审修订；具体文件／表布局在对应实施阶段确定，不能宣称现有 `analysis.json` 已包含完整图或评审记录。

报告围绕审核问题组织：候选需求 → 已确认目标与约束（如有）→ 前后行为 → 组间／消费者影响 → 重点问题与代码 → 双方判断／分歧 → 覆盖缺口。

- 业务说明不罗列实际代码路径；路径、固定 SHA、侧别和技术关系放入证据定位。
- 重点人工评审项直接嵌入差异及前后各 30 行；消费者和交叉两端在有需要时同时展示。当前实现主要链接独立证据，内联展示仍待补齐。
- 相邻窗口合并，重复代码用证据引用去重。长方法／大文件保留完整证据文件及精确未展示范围，不能静默裁切。
- 状态中区分“已发现”“已提供给模型”“模型已分析”“人工已确认”；未启用模型仍可阅读静态事实。
- 两类覆盖分别展示：底账登记完整性与依赖／影响分析范围。登记完成不能证明业务无遗漏。

## 9. 验收、规模与审核效果（G7）

### 9.1 必须补充的预标注案例

使用预先标注的本地 Git 样例和固定版本，分别标注变化、允许的分组／拆分、关系边、已知消费者、无关候选、必要证据与预期状态。分组允许多种合理答案，不为最少组数优化。以下均为计划验收，尚未在本轮运行。

| 案例 | 必须验证的结果 | 对应缺口 |
| --- | --- | --- |
| A 调用 B 且都变化、分别属于两组 | 保留两侧实际边及组间交叉，不被多源起点吞掉 | G1 |
| 菱形调用、环路、多个变化到达同一消费者 | 各来源可追溯；限制代表路径不丢已知边；触顶显式记录 | G1 |
| 旧版独有调用／删除方法／未变更 B | 两侧具体调用均保留；向导与非交互同 SHA 证据项目一致 | G3 |
| 相同方法名与参数数量、不同接口或服务绑定 | 保留候选和缺失绑定，不升级为确定依赖或部署事实 | G3 |
| A 改状态，B 的判断超出 30 行窗口 | 取相关方法、类型及 B 代码；取不到则证据不足 | G2 |
| 31 关联项、31 消费者、超长类型／提交／提示 | 逐类记录省略 ID／范围，总体截断为真；总输入符合预算 | G2 |
| JDK 缺失、扫描器无法启动、单项目 Git 失败、渲染失败 | 已落盘事实保留；按项目／阶段报告部分完成和可重试范围 | G4 |
| 无权威目标、目标被人工修订、SHA 相同但输入变化 | 符合性未确定或需重审；保留旧判断，AI 认可不代替批准 | G5 |
| 人工和 AI 对分组／需求／影响有不同判断 | 维度独立，重启后可读，分歧不被覆盖 | G5 |
| 无任务号、混杂提交、一个 Hunk 对应两需求 | 有依据的建议可修订；拆分可追溯且没有底账丢失 | G6 |
| 共享公共工具、完全回退、纯改名、二进制 | 不因连接强合组；只按最终净变化登记并披露解析限制 | G6 |
| 模型未运行／失败、关系遍历和补证预算用尽 | 静态报告仍可用；未覆盖范围和调用次数可核对 | G2 / G4 |

### 9.2 记录什么

与功能规格 SC-001～SC-007 配套，分开记录：底账遗漏和范围缺口、分组误合／误拆数量、已知消费者发现与漏检、无关候选、证据双端是否提供、未分析对象、人工拆合／修正次数、审核用时及最终遗留问题。模型引用合法率只是结构指标，不作为影响正确率。

用同一批变化对照逐文件审核和报告审核，并记录审核者背景和答案修正，防止只比较速度而忽略漏项。误合／误拆由预标注可接受分组或人工裁定计算；样本和支持类型明确后再统计比例，不宣称未知系统的业务召回率。

### 9.3 基准规模与预算

先建立下列候选规模用于压力和降级评测；这是计划样本档位，不是当前支持上限或性能承诺。每档还需记录源文件总量、AST 节点／关系边／调用点、组数、消费者及证据字节数。

| 档位 | 项目数 | 变化文件数 | 最终 Hunk／文件事件数 |
| --- | ---: | ---: | ---: |
| S | 3 | 50 | 200 |
| M | 10 | 500 | 2,000 |
| L | 20 | 2,000 | 10,000 |

固定每次评测的配置清单：Git／文件大小限制、提交数、图构建与查询节点／边／来源传播预算、取证字节与展开深度、模型输入／输出预算、调用组数及补证轮数。先记录当前默认值，再评估调整；不得从较小数据的成功推出 L 档已支持。

分别测 Git／AST／关系／取证／模型／渲染耗时、峰值内存、缓存命中与预算触顶后的产物。首期不设无依据的准确率、耗时 SLA 或提效百分比；但确定性案例中的已知直接边、底账和显式遗漏披露必须符合预标注结果。

## 10. 实施顺序与工具引入

| 顺序 | 工作包 | 交付与出口 |
| --- | --- | --- |
| P1-A | 底账先落盘、阶段／项目隔离、报告重建 | 无 JDK 仍有 Git 证据；单项目失败不抹去其他项目结果 |
| P1-B | 两侧关系边和未解析调用、统一证据项目输入、图查询 | A 调用 B 且都变化、旧版独有消费者、同 SHA 输入案例通过 |
| P1-C | 关联方法／类型／契约／消费者取证，整个输入预算 | 双端证据可追溯；所有类别的省略及补证失败可核对 |
| P2-A | 目标输入、维度化人工／AI 记录、修订适用性 | 无目标不判符合需求；目标／组／证据变化后正确重审 |
| P2-B | 归组建议、人工拆合、Hunk 细分及重算 | 无任务号案例减少碎片且不增加误合，底账可追溯 |
| 持续评估 | 预标注样例、噪声与审核对照、规模基准 | 每次规则增量都有正确性和负担变化数据 |
| 按需增强 | 类型／接口／实现绑定、两侧重构映射、范围内歧义追踪 | 由失败案例决定投入，不作为基础闭环前置条件 |
| 首期之后 | 更早历史统计、预计合并分析、Web、跨层血缘及执行验证 | 另行确定范围与验收，不能写成现有能力 |

先实施最小的 P1-A 与 P1-B，并补对应确定性回归；随后完成证据供给和评审记录。精确 Hunk→commit 归因后置，不再作为最高优先级任务。需求目标／分组反馈可以在 CLI 上落地，不依赖更换技术栈。

# 开发计划 v2.0：从 MR 静态影响分析到版本业务差异验证

> 更新时间：2026-10-19；这是**待执行的开发计划**，不是功能完成记录。  
> 约束：先保证每阶段产物可以单独使用；业务系统仍可运行 Java 8 / Dubbo 2.6.4 / ES 6.4.2；首期使用 Windows 原生 Python CLI，避免大规模重写。

## 0. 重新排序的理由

原计划更侧重“Java 调用图 → 中间件全覆盖 → AI → 测试”。现在的目标是**版本业务正确性**，所以中间应提前建设“版本清单、业务场景及其预期行为契约”，避免后续差异执行器只能比较一堆缺乏业务意义的原始数据。

新版严格分六阶段：

~~~text
P0-S 稳定可用的现有原型
  → P1-V 版本整体代码变更
  → P2-D 跨项目业务依赖与影响
  → P3-C 版本业务契约和场景规划
  → P4-E 受控 V1/V2 行为差异执行
  → P5-A AI 业务评审与持续运行
~~~

允许 P2 部分资源采集与 P3 的基础场景库并行，但 **P4 执行必须有批准的预期行为或明确 UNKNOWN 处理策略**。V1/V2 代码可执行不代表能够判断是否正确。

**现有能力**：`review-mrs`、`review-local`、Java AST、保守方法调用反查、API 版本规则、`--catalog`、Markdown/JSON；Windows 本地基础测试已有实测通过记录。

## P1-V：Release Manifest 与多个 MR 的联合候选版本

**问题**：多个 MR 的独立 diff 不是最后将上线的代码；生产 V1 的 SHA 也不一定等于这些 MR 的共同祖先。

### 工作项（按顺序）

- [ ] P1-V01：定义 `ReleaseManifest` JSON Schema：需求 ID、MR URL、每个项目 baseline SHA、候选 SHA、API Jar/依赖锁定、schema 迁移清单、配置 hash、目标环境与部署顺序。
- [ ] P1-V02：区分 `MR_DIFF_BASE`、`PRODUCTION_BASELINE`、`RELEASE_CANDIDATE` 三个概念，构建唯一版本标识和 manifest hash。
- [ ] P1-V03：同仓库多个 MR 按声明顺序模拟合并，获得**临时合并提交/候选树**；不能合并时输出精确冲突项目与文件；不写回上游 GitLab。
- [ ] P1-V04：跨仓库统一归属“本次版本”和部署兼容关系；检测服务使用的 API Jar 版本、修改 API 未提升版本的规则及消费者依赖冲突。
- [ ] P1-V05：扩充变更类型：逻辑、接口、DTO、配置、SQL、MQ 消息、数据库 schema、前端文件；暂无法精确分析的类型标记“专项待确认”。
- [ ] P1-V06：输出**版本级主要改动摘要**：一个业务需求跨项目多个方法变化合并成一个可审查的影响描述，要求至少保留原始代码事实和待人工补充的业务语义。
- [ ] P1-V07：分析任务持久化初期可用文件 JSON，保证重复相同 manifest 能回放报告；随后按性能需求迁移 MySQL。

### 关键实现入口

新增 `diff_analysis/manifest.py`、`merge_plan.py`、`change_types.py`；调整 `cli.py` 支持 `review-release --manifest ...`（**计划命令，当前不存在**）；保留现有 `review-mrs` 不破坏兼容。

### 验收场景

- 同仓库 MR-A 修改状态判断，MR-B 修改同一文件但不冲突：应在最终候选中正确体现两项变更。
- MR-A 与 MR-B 同行冲突：标记 `CANDIDATE_CONFLICT`，不得伪造“已经合并”。
- 项目 A 使用新 API Jar、项目 B 仍锁定旧 Jar：版本报告中列出兼容风险。
- 生产版本落后于 MR target：报告中分别列出 Git MR 改动和实际生产→候选的差异。

### 验收出口

**无需执行真实业务代码**，也能得到准确的版本代码变化、组合风险和源证据。所有 SHA、配置、依赖版本可复查。

## P2-D：跨项目资源依赖和条件依赖

**问题**：未知程序 D 可能不调用 A/B/C，却读取 C 写入的数据或 MQ/Redis 资源。**不要先追求全部中间件覆盖，按支付风险优先。**

### 工作项

- [ ] P2-D01：改善 Java 调用精度：包名/类型、接口实现、依赖注入、方法签名、重载、项目和 Jar 坐标；无法解析保留候选，不再仅凭名称连线。
- [ ] P2-D02：建立带版本的 `DependencyNode`、`DependencyEdge`、`DependencyEvidence` 存储（初期 SQLite/MySQL 均可）；保留证据来源和失败缺口。
- [ ] P2-D03：识别 Dubbo API/provider/consumer 和 ZK 注册证据；复用现有 Filter/traceId 采集，不要求改业务版本。
- [ ] P2-D04：为 MyBatis XML、注解 SQL、可识别 JDBC SQL 建表/字段级 `READS`、`WRITES` 和 `READS_CONDITION`，覆盖 WHERE/JOIN/HAVING 的关键字段。
- [ ] P2-D05：RabbitMQ producer/exchange/routing key/binding/queue/consumer 关系，识别消息格式变更；动态路由和运行时配置留未知。
- [ ] P2-D06：Redis Key 模式/读写/值结构兼容性；防止把同一个前缀误认为同一个资源，记录环境与实例。
- [ ] P2-D07：根据变更方法及资源 effect，反向找到未修改仓库和业务入口；按需补扫代码，不要求一次扫描全公司。
- [ ] P2-D08：后续扩展 ES 业务/监控索引、XXL-JOB、Oracle SQL、前端 JS/Vue/CSS；避免把日志读取与支付业务读写混同。

### 必须保留的判断原则

- `STATIC` / `RUNTIME` / `CONFIG` / `INFERRED` 证据状态可并存；“未观测到”不等于“无依赖”。
- 旧新图谱取并集，被删除的关系同样需要分析。
- MQ 消费者不存在于当前 MR 不意味着必须修改；要检查消息契约是否兼容。
- SQL 读写需要带数据源实例、schema、表字段及条件，以防无关同名表造成大规模误报。

### 验收用例

1. A 调用 B，B 调用 C，D 通过读取 `trans_record.trans_state` 被影响：D 应进入评审范围，即使 D 没提交 MR。
2. 修改 RabbitMQ 生产消息字段：已纳管的消费者可以被找到，缺少配置证据的消费者标记待确认。
3. 修改同名但不同 schema 的表：不应把两个库的消费者错误关联。
4. 删除旧调用边：旧图中曾有依赖关系，报告仍需解释潜在影响。

### 验收出口

产生可解释的跨项目影响路径、每条路径的代码/配置/运行证据和未覆盖统计。

## P3-C：业务场景库与版本契约确认（优先于大规模执行框架）

**问题**：既然测试的期望不能由待测实现自行决定，就要先有业务契约来源、审批状态以及可重用场景目录。

### 工作项

- [ ] P3-C01：定义稳定 `scenario_id`、领域、业务入口、前置条件、输入 fixture、标准化断言、副作用期望、标签和 owner。
- [ ] P3-C02：场景库初始覆盖支付、退款、查询、通知、对账、签约，先各选少量高价值场景；现有测试通过 adapter 复用，不全部重写。
- [ ] P3-C03：定义 `BehaviorContract` 状态：`NEW`、`CHANGED`、`UNCHANGED`、`UNKNOWN`。每次版本绑定需求 ID、批准人、审批依据及契约版本。
- [ ] P3-C04：从影响图映射到业务入口，再检索长期场景；选择必须回归的已有功能和当前缺失的场景。没有影响路径的高风险入口仍可由规则强制纳入。
- [ ] P3-C05：允许 AI 提议新场景和输入边界（仅草案），但 **AI 不得直接批准期望值或将源码输出当答案**。
- [ ] P3-C06：实现“版本回归计划”报告：新增测试、改变期望、保持不变、未确认、缺少测试、受影响业务入口及对应依赖证据。
- [ ] P3-C07：给场景建立“Mock 边界说明”：哪些是真实内部依赖，哪些是模拟的外部渠道；登记风险和覆盖缺口。
- [ ] P3-C08：支持高风险场景优先级（金额、幂等、失败重试、退款次数、账务/对账、异步补偿），避免机械追求生成测试数量。

### 最小验收案例

**需求**：支付成功状态增加 `SUCCESS`。  
**版本契约**：旧状态支付查询 `UNCHANGED`；新状态支付查询 `CHANGED/NEW`（取决于历史入口）；原支付后退款流程 `UNCHANGED`；对账消费者状态为 `UNKNOWN`，待确认“新状态成功交易是否纳入对账”。

必须输出：
- 新状态对应的业务输入和预期持久化字段；
- 旧状态场景的回归列表；
- 需要人批准的 UNKNOWN 项；
- 不要生成已经“通过”的测试记录。

### 验收出口

在 **完全没有执行 V1/V2 的条件下**，也能输出经批准的“本版本业务契约与回归验证计划”。这本身就是一个有价值的人工评审产物。

## P4-E：差异执行器：从单个隔离业务场景开始

这是成本最高、也是最容易出现“Mock 太多失去业务意义”的阶段。要从**最小纵切面**验证，而不是同时支持所有服务、中间件和入口。

### P4-E1：最小可运行切面

- [ ] P4-E101：选择单一场景：例如“支付成功后的部分退款”或“成功交易对账读取”。业务输入、初始状态和期望行为必须已经通过 P3-C 审批。
- [ ] P4-E102：建立 V1/V2 两套相互隔离环境；各自的业务程序、DB schema/实例、配置都来自锁定版本清单，不能共享修改性存储。
- [ ] P4-E103：由同一规范化 fixture 初始化 V1/V2，控制业务时间、渠道返回和外部请求。绝不连接真实银行或支付公司渠道。
- [ ] P4-E104：尽量真实执行内部 Service 和 Mapper；初始阶段只模拟**最外层银行渠道**，记录请求意图及渠道模拟响应。
- [ ] P4-E105：采集返回码、业务响应、DB 关键行列最终状态及渠道调用意图（金额/次数/幂等键）。
- [ ] P4-E106：实现基础语义比较：业务键对齐、金额精度、UUID/自增 ID/时间规范化、批准忽略字段、预期内/非预期变化。
- [ ] P4-E107：区分 `INCOMPARABLE`、`EXECUTION_FAILED`、`NOT_EXECUTED`，不能把环境/脚本失败解释成业务差异或执行通过。
- [ ] P4-E108：保存完整测试追溯：SHA、fixture/contract hash、运行环境、mock 脚本、输出摘要和比较策略版本。

**P4-E1 通过条件**：人为植入“退款调用重复两次”“少写一条退款记录”“金额写错”等缺陷，比较器能在对应维度识别异常并关联证据；对于准许变化不报缺陷；无真实支付副作用。

### P4-E2：复杂行为扩展

- [ ] P4-E201：支持 Redis 幂等 Key/TTL 比较、MQ 消息数量/内容/路由比较。
- [ ] P4-E202：支持 RabbitMQ/XXL-JOB 异步完成条件、事件顺序/因果约束、最终一致性观测窗口，避免立即对比造成误报。
- [ ] P4-E203：支持超时、重试、未知渠道状态、回调丢失和故障注入，比较最终状态及外部调用次数。
- [ ] P4-E204：支持数据库 schema 迁移适配：按批准的业务字段映射比较，不对无业务意义的新旧表结构机械逐字段比对。
- [ ] P4-E205：有选择地增加 HTTP、Dubbo、MQ 入口，以及多服务交易链路；每个扩展都保留真实/Mock 边界报告。
- [ ] P4-E206：对环境难以隔离的场景只给“无法自动执行 + 人工验证建议”，不强制构造不可信的全 Mock 测试。

### V1/V2 比较不得违反的规则

1. 初始状态等价、外部返回序列可控，才允许比较；否则标记不可比较。
2. 动态主键可归一化，但不能忽略金额、状态、交易关联、消息数量和外部调用次数。
3. 无差异 ≠ 正确：如果 CHANGED 要求新行为，但 V2 没有实现，也应报告“缺少预期变化”。
4. 有差异 ≠ Bug：如果有经批准的 CHANGED 契约，检查差异是否符合它。
5. 历史生产数据只允许经过批准的脱敏/合成 fixture，不能使用生产交易密钥、真实扣款通道。

## P5-A：AI 评审与产品化（可分独立子项目）

- [ ] P5-A01：AI 基于真实代码证据解释修改的业务行为；按需展开相关服务/消费者方法，而不是把所有 Git Diff 一次性塞入上下文。
- [ ] P5-A02：AI 对 P3-C 合同 UNKNOWN 和 P4-E 比较异常提出候选原因、遗漏改动位置和补充测试建议。
- [ ] P5-A03：报告以“版本主要影响 → 重要遗漏 → 合同矩阵 → 回归/差异结果 → 未覆盖风险”为顺序，每项可链接到 GitLab SHA 和执行证据。
- [ ] P5-A04：AI 输出结构化 Finding Schema，强制区分 CODE_EVIDENCE、EXECUTION_EVIDENCE、HYPOTHESIS、UNKNOWN。
- [ ] P5-A05：加入人工反馈：误报、已确认兼容、需求允许改变、需新增场景；保留审核记录。
- [ ] P5-A06：GitLab MR 评论与 Web 页面只在读取和报告流程稳定后引入，不为 UI 重写核心分析引擎。
- [ ] P5-A07：尝试 selective execution（根据影响图选择场景），但对支付退款/金额/幂等风险始终有保守必测集合。
- [ ] P5-A08：与既有回归测试及 CI 结合，失败/未知时提供人工门禁建议；不基于 AI 推断自动批准上线。

## 7. 第一批场景资产（建议）

| scenario_id（示意） | 核心验证 | 层级 |
| --- | --- | --- |
| `payment.success.repeat_same_trade` | 重复支付请求不能形成多次真实渠道意图 | 高风险 |
| `payment.timeout.query_and_recover` | 状态不确定时不得直接重复扣款 | 高风险 |
| `refund.partial.amount_limit` | 部分退款累计金额不得超额 | 高风险 |
| `refund.timeout.retry_idempotency` | 退款超时重试不得重复退款 | 高风险 |
| `notification.success.retry` | 通知重试次数、状态和 MQ 事件符合规则 | 关键 |
| `reconciliation.read_success_states` | 对账应涵盖所有批准的成功交易状态 | 高风险 |
| `sign.agreement.status_transition` | 签约状态、短信及确认流程符合业务需求 | 关键 |

以上场景的具体金额、状态、重试次数及预期均**需要业务审核**，不能照表直接拿来自动断言。

## 8. 验收数据集与评测原则

### 静态分析金标准样例

- 同类方法直接调用、接口多实现、Dubbo 代理、MyBatis XML、RabbitMQ 生产/消费、Redis Key 写读。
- D 不调用 C，但通过数据库 WHERE 条件读取 C 写入的状态；应检出跨服务影响。
- 同名但不同数据源/Schema、同名方法但不同全限定类型：应避免虚假影响。

### 版本差异执行金标准样例

- **应检出**：多一次退款意图、少一条持久化记录、错误成功状态、遗漏通知、对账漏单。
- **应忽略但可追溯**：批准的 traceId/创建时间变化、记录 ID 映射差异。
- **应标记未知**：缺少相同初始 DB fixture、某个渠道模拟结果不一致、异步消息尚未完成。

每个金标准案例必须有**预期输出和已知缺陷类型**；仅运行全部测试 `PASS` 不能证明漏报率可接受。

## 9. 下一轮最有价值的开发任务

按照下列顺序执行，避免直接跃迁到昂贵的双版本环境：

1. **先完成 P0-S01 与 P0-S03**：真实内网多 MR 样本 + 一个“未知 D”验证样例。确认现在的分析报告究竟能发现什么。
2. **接着完成 P1-V01/V02/V03**：固定版本清单与候选合并；不解决基线问题，后续 V1/V2 对比难以复现。
3. **同时设计 P3-C 的最小 `BusinessScenario` 和 `BehaviorContract` Schema**：选一条退款/对账场景，让业务认可预期。
4. **然后针对这条场景补 P2-D 的必要资源关系**：不要求先完整部署所有中间件采集器。
5. **最后实现 P4-E1 最小闭环**：一个受控渠道 Mock、真实内部 SQL 和 DB 记录、一个端到端差异报告。

### 最小产品里程碑

给定一个版本的 MR 集合、一个经批准的业务场景和两组可复现环境，系统可以：

- 说明代码实际改了什么、影响到哪些未修改消费者；
- 明确场景是 NEW/CHANGED/UNCHANGED/UNKNOWN；
- 在允许执行时展示 V1/V2 的业务行为及关键副作用差异；
- 给出是否符合契约的证据，或明确说明“尚未验证/无法比较”。

**这才是新架构的验收终点，而不是“AI 生成的单元测试全部为绿色”。**
